The YAMLPolicyEngine then evaluates against that PolicyConfig at runtime (hot path). regopy.query() is NEVER called on the hot path.

Create `src/cloneguard/enforcement/backends/cedar.py`:

Module docstring: "Cedar policy backend -- compiles Cedar policies to PolicyConfig IR (D-01, D-02, GOVN-02). Uses cedarpy (Rust Cedar engine with Python bindings via PyO3) for in-process policy validation. Designed for AWS Bedrock AgentCore integration."

**Cedar compilation design (per D-02 and research open question #2):**

Cedar's native model is permit/forbid on principal-action-resource triples. This doesn't map directly to PolicyConfig's threshold-based model. The solution: Cedar policies for CloneGuard use a **convention-based entity schema** where policy configuration is encoded as entity attributes on a CloneGuard-specific entity.

The Cedar policy file contains TWO sections:
1. A JSON entities block (as a separate string or inline) defining the configuration entity
2. Cedar policy statements that the backend validates for syntax

The backend extracts configuration from the entities, NOT from policy evaluation. The Cedar policies themselves are validated for syntax correctness and stored alongside the PolicyConfig for future use (when Cedar evaluation is needed for advanced permit/forbid rules).

`CedarPolicyBackend` class:

1. `__init__(self)`: Import `cedarpy` at construction time. If ImportError, raise `ImportError("cedarpy not installed. Install with: pip install 'cloneguard[cedar]'")`.

2. `name` property: returns `"cedar"`

3. `compile(self, source: str) -> PolicyConfig`:
   - The `source` string is a YAML document (not raw Cedar syntax) that contains:
     - `policies`: Cedar policy text (validated for syntax)
     - `config`: PolicyConfig-compatible dict (thresholds, enforcement, etc.)
   - Parse the YAML wrapper with `yaml.safe_load(source)`
   - Validate Cedar policy syntax using `cedarpy.is_authorized()` with a test request, or use `cedarpy.validate_policies()` if available
   - Extract the `config` dict and pass to `PolicyConfig.model_validate(config_dict)`
   - On parse/validation error, raise `ValueError` with descriptive message

   **Alternative simpler approach (preferred):** If the cedarpy API makes syntax validation difficult, use a simpler pattern: the Cedar "policy file" is a YAML document with a `cedar_policies` field (raw Cedar text, validated) and standard PolicyConfig fields. This keeps Cedar syntax validation separate from configuration extraction.

4. `validate(self, source: str) -> list[str]`:
   - Try `self.compile(source)`, return `[]` on success
   - Catch ValueError and return `[str(e)]`

**Key design decision:** Cedar is permit/forbid, PolicyConfig is threshold-based. Rather than trying to extract thresholds from Cedar evaluation results (which would require calling is_authorized on the hot path, violating D-02), the Cedar backend uses a YAML wrapper document that includes both Cedar policy text (for syntax validation and future advanced evaluation) and explicit PolicyConfig values. This is the same pattern as OPA: the policy language is a DATA source for configuration values, not the runtime evaluator.
