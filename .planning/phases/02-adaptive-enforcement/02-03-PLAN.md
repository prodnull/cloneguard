<objective>
Implement OS-level sandbox adapters for Linux (Landlock LSM) and macOS (Seatbelt), plus the `cloneguard-sandbox-exec` wrapper binary that applies restrictions before exec'ing the target command.

Purpose: These adapters provide real OS-level enforcement. The critical architectural insight (resolved from RESEARCH.md Open Question 1) is that CloneGuard does NOT spawn the tool subprocess -- the agent does. Therefore, sandbox restrictions cannot be applied via `preexec_fn` in the hook handler. Instead, the enforcement model uses a **wrapper binary approach**: when enforcement is active, the hook handler writes a constraint spec to a session-scoped temp file, and the agent's Bash command is executed through `cloneguard-sandbox-exec` which reads the constraints, applies Landlock/Seatbelt restrictions to its own process, then exec's the original command. This preserves the hook protocol contract (exit 0/2 only) while achieving real OS-level enforcement.

The `cloneguard-sandbox-exec` binary is installed alongside CloneGuard (same package, new entry point). It is invoked as a shell wrapper -- either via `cloneguard setup` configuring the agent's shell to route Bash through it, or explicitly by the operator.

Output: LandlockAdapter, SeatbeltAdapter, and sandbox_exec modules. Adapters implement `restrict_filesystem()` and `restrict_network()` to store desired constraints, plus `apply_restrictions()` which applies them to the current process (called only from within the sandbox-exec wrapper). The sandbox_exec entry point deserializes constraint specs and applies them.
</objective>

  <action>
    **Architecture change from original plan:** Adapters NO LONGER produce `get_preexec_fn()` callables. Instead, they implement:

    1. `restrict_filesystem()` / `restrict_network()` -- store desired constraints (same as before)
    2. `apply_restrictions()` -- apply OS-level restrictions to the CURRENT process (called only from within `cloneguard-sandbox-exec` wrapper, never from the hook handler)
    3. `serialize_constraints()` -- return a JSON-serializable dict with adapter name, stored paths, and any adapter-specific config. This is what gets written to the constraint spec file.

    **Why the change:** CloneGuard does not spawn the tool subprocess (RESEARCH.md Open Question 1, RESOLVED). The agent spawns it. The wrapper binary `cloneguard-sandbox-exec` is a separate process that the agent's command is routed through. It calls `apply_restrictions()` on itself, then exec's the target command. Since `cloneguard-sandbox-exec` IS the target process (it exec's the command), restrictions applied to it persist into the exec'd command.

    **Create src/cloneguard/enforcement/landlock.py:**

    Same ctypes-based Landlock implementation as the original plan, but with `apply_restrictions()` instead of `get_preexec_fn()`.

    Key constants (x86_64 and aarch64 use same syscall numbers):
    - SYS_LANDLOCK_CREATE_RULESET = 444
    - SYS_LANDLOCK_ADD_RULE = 445
    - SYS_LANDLOCK_RESTRICT_SELF = 446
    - PR_SET_NO_NEW_PRIVS = 38
    - LANDLOCK_RULE_PATH_BENEATH = 0x01
    - Filesystem access flags: READ_FILE=0x04, WRITE_FILE=0x08, READ_DIR=0x10, EXECUTE=0x01, MAKE_REG=0x40, MAKE_DIR=0x80

    Minimum always-allowed paths (Pitfall 2 from research):
    - Always writable: /tmp
    - Always readable: /tmp, /proc, /dev/null, /dev/urandom, /dev/zero, /usr/lib, /usr/local/lib, /lib, /lib64, /etc

    The `apply_restrictions()` method:
    1. prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)
    2. landlock_create_ruleset with handled_access_fs bitmask
    3. landlock_add_rule for each readable path (READ_FILE | READ_DIR)
    4. landlock_add_rule for each writable path (READ_FILE | WRITE_FILE | READ_DIR | EXECUTE | MAKE_REG | MAKE_DIR)
    5. landlock_restrict_self(fd, 0)
    6. Close all opened fds

    If any syscall fails (returns -1 with errno), the method returns silently (graceful degradation -- better to run unconfined than to crash the tool).

    **Create src/cloneguard/enforcement/seatbelt.py:**

    Same ctypes-based Seatbelt implementation as the original plan, but with `apply_restrictions()` instead of `get_preexec_fn()`.

    The `apply_restrictions()` method:
    1. Generate SBPL profile via `_generate_profile()`
    2. Call sandbox_init_with_parameters from libSystem.dylib
    3. If ret != 0, return silently (graceful degradation)

    SBPL profile generation (deny-default + selective allow):
    - (version 1) header
    - (deny default) baseline
    - (import "bsd.sb") standard BSD operations
    - Always-allowed process execution (/bin, /usr/bin, /usr/sbin)
    - Always-allowed system libraries (/usr/lib, /usr/local/lib, /Library/Frameworks, /System/Library)
    - Always-allowed temp paths (/tmp, /private/tmp, /private/var/folders)
    - Readable paths as (allow file-read* (subpath "..."))
    - Writable paths as (allow file-read* file-write* (subpath "..."))
    - Network: if network_allow is non-empty, allow network-outbound. If empty, deny default blocks all.

    Path escaping: _escape_sbpl_path(path: str) -> str helper doubles backslashes and escapes double-quotes.

  <action>
    Create `src/cloneguard/enforcement/sandbox_exec.py` -- the wrapper binary that applies OS sandbox restrictions before exec'ing a target command.

    **Usage:**
    ```
    cloneguard-sandbox-exec --spec-file /tmp/cg-enforce-XXXX.json -- bash -c "npm install express"
    ```

    **How it works:**
    1. Parse args: `--spec-file <path>` or `--policy <base64-json>`, then `--`, then the target command
    2. Read constraint spec (JSON with fields: adapter, writable, readable, network_allow)
    3. Call `get_sandbox_adapter(preferred=spec["adapter"])` to get the right adapter
    4. Call `adapter.restrict_filesystem(writable=spec["writable"], readable=spec["readable"])`
    5. Call `adapter.restrict_network(allow=spec["network_allow"])`
    6. Call `adapter.apply_restrictions()` -- applies Landlock/Seatbelt to THIS process
    7. Delete the spec file (one-shot; prevents replay)
    8. `os.execvp(target_cmd[0], target_cmd)` -- replaces this process with the target command, which inherits the sandbox restrictions

    **Key design decisions:**
    - `--spec-file` is preferred over `--policy` for production (avoids leaking constraints in process list)
    - The spec file is deleted after reading (prevents stale enforcement on retry)
    - Any failure in steps 2-6 logs a warning and falls through to exec without restrictions (fail-open, matching NoopAdapter behavior)
    - This is a standalone entry point registered in pyproject.toml

    **Add entry point to [project.scripts] in pyproject.toml:** `cloneguard-sandbox-exec = "cloneguard.enforcement.sandbox_exec:main"`

    **Helper function for hook handler integration (Plan 05):**

    ```python
    def write_constraint_spec(constraints: dict[str, Any]) -> str:
        """Write serialized constraints to a temp file. Returns the file path.

        The spec file is used by cloneguard-sandbox-exec --spec-file.
        Caller is responsible for ensuring the spec file path reaches the
        sandbox-exec invocation (via environment variable or command prefix).

        import tempfile

        fd, path = tempfile.mkstemp(prefix="cg-enforce-", suffix=".json")
        with os.fdopen(fd, "w") as f:
            json.dump(constraints, f)
        return path
    ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Hook handler to sandbox-exec wrapper | Constraint spec file transports enforcement directives across process boundary |
| sandbox-exec to OS kernel | apply_restrictions() makes raw syscalls / dylib calls at the OS boundary |
| Constraint spec file on disk | Temp file contains enforcement directives; must not be tampered with |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-11 | Elevation of Privilege | CloneGuard restricts itself | mitigate | apply_restrictions() is ONLY called from cloneguard-sandbox-exec, which exec's the target command afterward. The hook handler process never calls apply_restrictions(). Verified by test that hook handler only writes spec files, never applies restrictions. |
| T-02-12 | Elevation of Privilege | Symlink escape from sandbox | mitigate | Landlock resolves symlinks natively (kernel built-in). Seatbelt: paths canonicalized with Path.resolve() before embedding in SBPL profile. |
| T-02-13 | Denial of Service | Sandbox breaks tool usage | mitigate | Always-allowed minimum paths (/tmp, /proc, system libs). Dry-run default (D-13). Graceful degradation: if sandbox application fails, target runs unrestricted (logged). |
| T-02-14 | Tampering | Constraint spec file race condition | mitigate | Spec file created with mkstemp (unique, 0600 permissions). Deleted immediately after read by sandbox-exec. Window is minimized. File path not predictable (random suffix). |
| T-02-15 | Tampering | SBPL injection via path strings | mitigate | All paths escaped: backslashes doubled, double-quotes escaped before embedding in SBPL. No eval or dynamic code generation in profile strings. |
| T-02-16 | Information Disclosure | Landlock ABI version leaks kernel info | accept | ABI version is minor info disclosure (kernel 5.13 vs 6.7). Logged at DEBUG level only. No security impact -- attacker already has uname. |
| T-02-17 | Tampering | Agent writes fake constraint spec | mitigate | Spec file path is only known to the hook handler that creates it. Agent would need to predict the mkstemp path. Enforcement is additive-only (constraints can restrict, never grant new permissions). Worst case: agent writes empty constraints, getting NoopAdapter behavior (already the default). |
</threat_model>
