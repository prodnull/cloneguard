<objective>
Wire the enforcement pipeline into the hook handlers and update audit emission.

Purpose: This plan connects all Phase 2 components into the live detection pipeline. After this plan, the full flow is: hook event -> DetectionEngine.scan() -> PolicyEngine.evaluate() -> write constraint spec for sandbox-exec (or dry-run log) -> NDJSON audit event with enforcement details. This is the integration layer that makes enforcement real.

The enforcement model uses the wrapper binary approach (RESEARCH.md Open Question 1, RESOLVED): the hook handler writes a constraint spec file when enforcement is active, and the `cloneguard-sandbox-exec` wrapper binary (from Plan 03) reads and applies it before exec'ing the target command. The hook itself never applies sandbox restrictions -- it only determines and records the policy decision.

Output: Updated hooks.py with enforcement integration, updated AuditEvent with DRY_RUN/CONSTRAIN/would_apply fields, public sandbox_preferred accessor on YAMLPolicyEngine, and end-to-end integration tests proving the full pipeline works.
</objective>

    **Step 4: Integrate policy evaluation and constraint spec writing into hook handlers in src/cloneguard/hooks.py**

    Add enforcement to handle_pre_tool_use (the primary enforcement point per the v2 architecture).

    The key change from the original plan: instead of calling `adapter.restrict_filesystem()` / `adapter.restrict_network()` (which would silently do nothing since CloneGuard does not spawn the subprocess), the hook handler writes a constraint spec file via `write_constraint_spec()`. The `cloneguard-sandbox-exec` wrapper binary (Plan 03) reads this file and applies the restrictions.

    ```python
    def handle_pre_tool_use(data: dict[str, Any]) -> int:
        """Handle PreToolUse hook -- thin shim with enforcement (Phase 2).

        Pipeline: DetectionEngine.scan() -> PolicyEngine.evaluate() -> enforcement
        Exit code unchanged: SAFE/SUSPICIOUS -> 0, MALICIOUS -> 2 (Pitfall 5)
        """
        engine = _get_bridged_engine()
        result = engine.scan_pre_tool_use(data)

        # Phase 2: Policy evaluation
        policy_decision = None
        try:
            from cloneguard.enforcement.policy import get_policy_engine
            from cloneguard.enforcement.adapter import get_sandbox_adapter

            policy_engine = get_policy_engine()
            policy_decision = policy_engine.evaluate(
                result,
                tool_name=data.get("tool_name", ""),
            )

            # Write constraint spec for sandbox-exec wrapper (only if not dry-run
            # and action is constrain). The spec file is consumed by
            # cloneguard-sandbox-exec which applies OS-level restrictions.
            if (
                policy_decision.action == "constrain"
                and not policy_decision.dry_run
            ):
                adapter = get_sandbox_adapter(
                    preferred=policy_engine.sandbox_preferred  # public property, not _config
                )
                # Build constraint spec for the wrapper binary
                from cloneguard.enforcement.sandbox_exec import write_constraint_spec
                spec = {
                    "adapter": adapter.name,
                    "writable": list(policy_decision.constraints.filesystem_writable),
                    "readable": list(policy_decision.constraints.filesystem_readable),
                    "network_allow": list(policy_decision.constraints.network_allow),
                }
                spec_path = write_constraint_spec(spec)
                # Set environment variable for the sandbox-exec wrapper to find
                import os
                os.environ["CLONEGUARD_ENFORCE_SPEC"] = spec_path
        except Exception:
            pass  # Enforcement failure must never break the hook pipeline

        if result.message:
            print(result.message)
        if result.exit_code != 0 or result.verdict != "clean":
            _emit_audit_event(data, result, "PreToolUse", policy_decision)
        elif policy_decision is not None and policy_decision.action != "allow":
            # Emit audit event for enforcement actions even when detection is clean
            _emit_audit_event(data, result, "PreToolUse", policy_decision)
        return result.exit_code
    ```

    CRITICAL: The exit code logic is UNCHANGED. SAFE/SUSPICIOUS -> 0, MALICIOUS -> 2 (Pitfall 5 from research). Enforcement happens outside the exit code channel. The constraint spec file is consumed by `cloneguard-sandbox-exec`; the hook still returns exit 0 for SUSPICIOUS. Only MALICIOUS produces exit 2.

    For handle_instructions_loaded and handle_post_tool_use: Add policy evaluation similarly but with simpler logic (InstructionsLoaded has no subprocess to sandbox; PostToolUse scans output after execution). Pass policy_decision to _emit_audit_event for audit trail completeness. Neither writes constraint spec files -- only PreToolUse does.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Detection result to policy engine | DetectionResult.verdict/confidence determine enforcement action |
| Policy decision to constraint spec file | PolicyDecision.constraints serialized to temp file for sandbox-exec |
| Constraint spec file to sandbox-exec | Temp file transports enforcement directives across process boundary |
| Enforcement outcome to audit | Audit event captures what was enforced (or would be enforced) |
| Hook handler to agent | Exit code (0/2) is the only signal to the agent |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-21 | Tampering | Enforcement bypass via import failure | mitigate | All enforcement imports wrapped in try/except. Import failure -> detection-only mode (v0.5.0 behavior). Logged. Never blocks agent or changes exit code semantics. |
| T-02-22 | Denial of Service | Enforcement adds latency to hook | mitigate | Policy evaluation is O(1) dict lookup. Constraint spec writing is a single file write (tmpfs). Dry-run default means zero enforcement overhead initially. |
| T-02-23 | Repudiation | Enforcement action not audited | mitigate | Every enforcement action (ALLOW/CONSTRAIN/BLOCK/DRY_RUN) is emitted as NDJSON audit event with constraints_applied or would_apply. Audit emission is best-effort (never blocks) but failures are logged. |
| T-02-24 | Elevation of Privilege | Exit code manipulation | mitigate | Exit code contract preserved exactly: SAFE/SUSPICIOUS->0, MALICIOUS->2 (Pitfall 5). Enforcement happens outside the exit code channel via constraint spec files. No new exit codes introduced. |
| T-02-25 | Information Disclosure | Dry-run leaks constraint config | accept | DRY_RUN audit events contain would_apply constraints (filesystem paths, network domains). This is intentional -- operators need to see what enforcement would do. Audit events go to operator-controlled NDJSON output, not stdout (hook channel). |
| T-02-26 | Tampering | Constraint spec file tampered between write and read | mitigate | Spec file created with mkstemp (0600 permissions, unpredictable name). Deleted immediately after read by sandbox-exec. Time window is minimized. Enforcement is additive-only (can restrict, never grant). |
</threat_model>
